# Разработка и сопровождение TeleRepka

Цель — добавлять функции без регрессий на основной Repka Pi. Перед работой прочитать [AGENTS.md](../AGENTS.md) и [CURRENT_STATE.md](CURRENT_STATE.md).

## Рабочий процесс Git

1. Проверить состояние: `git status --short --branch`, `git log -1 --oneline`.
2. Из актуальной `main` создать отдельную ветку для функции/исправления.
3. Изучить связанные исходники и существующие инструкции. Не менять аппаратные настройки «заодно».
4. Внести минимальные изменения, выполнить подходящие проверки и зафиксировать результаты.
5. Проверить `git diff --check`, `git diff --stat`, затем создать коммит.
6. Отправить ветку на GitHub, открыть PR, объединить после проверки; на плате обновить `main` через `git pull --ff-only origin main`.

Пример:

```bash
cd ~/git/TeleRepka
git status --short --branch
git switch main
git pull --ff-only origin main
git switch -c feature/short-description
# изменения и проверки
git diff --check
git status --short
git add <нужные-файлы>
git diff --cached --check
git commit -m "feat: describe change"
git push -u origin feature/short-description
```

Не выполнять `git clean -fd`, `git reset --hard` или force-push для устранения локальных файлов без согласования. В частности, `backups/` и другие неотслеживаемые файлы на плате могут быть нужны.

## Проверки по компонентам

| Изменение | Минимальная проверка |
|---|---|
| Python (`app.py`, `employees.py`, `schedule_parser.py`) | `.venv/bin/python -m py_compile app.py employees.py schedule_parser.py laboratory_sync.py` |
| API сотрудников | `curl -fsS http://127.0.0.1:5000/api/employees`; проверить ожидаемый JSON |
| SQLite | Проверить `data/laboratory_employees.db`, схему и количество записей; не изменять продуктивные данные тестами |
| Синхронизация сотрудников | Сначала `.venv/bin/python laboratory_sync.py` без `--apply`; записывать только при осознанном подтверждении |
| Интерфейс | Проверить список, поиск, выбор сотрудника, повторное нажатие зелёной кнопки |
| ТВ / WebRTC | Проверить вход в комнату ТВ, старт/остановку трансляции, полный экран и возврат к панели |
| CDP / управление | Проверить `127.0.0.1:9222/json/list`, предпросмотр и управление, не ломая активную трансляцию |
| Киоск / GPU / звук | Отдельное тестирование на реальном устройстве с возможностью отката |
| Развёртывание | `bash -n deploy/install.sh deploy/check.sh`; `deploy/install.sh` не запускать на основной плате |

Автоматизированного полного интеграционного тестового набора в просмотренных файлах не обнаружено. Успешная компиляция Python не заменяет проверку на ТВ.

## Обновление рабочей платы

- Перед изменением действующих `app.py`, `templates/index.html` и systemd-конфигурации сохранить состояние и понять способ отката.
- Для изменения только Markdown-документации перезапуск сервиса не требуется.
- Для изменений Python или шаблона может потребоваться `sudo systemctl restart lab-hub-kiosk.service`; это кратковременно разрывает Socket.IO/WebRTC-сеансы.
- После обновления шаблона проверить, что сервер отдаёт новую HTML-версию, и обновить страницу ТВ/рабочего браузера; кеш Chromium может сохранять старую страницу.
- Не перезапускать GDM, Chromium или плату ради обычных изменений API и интерфейса.
- Проверить `sudo bash deploy/check.sh` и пользовательские сценарии, затронутые изменением.

## Данные и безопасность

- Локальная SQLite-база: `data/laboratory_employees.db`; её нельзя включать в коммиты.
- Для переноса и резервного копирования следовать [deploy/README.md](../deploy/README.md). Не заменять файл БД при активной записи.
- Не коммитить пароли, секреты, ключи, сертификаты и резервные копии.
- Внешний HTTPS и прокси настраиваются отдельно; не предполагать, что локальный Flask безопасно доступен извне.
- Приложение на основной плате работает с повышенными привилегиями из-за аппаратного GPIO; изменения в HTTP-маршрутах и управлении системой требуют особого внимания.

## Принципы изменений

- Сохранять совместимость с работающей аппаратной конфигурацией.
- Отделять подтверждённые факты от предположений и планов.
- Не выдавать наличие кода за доказательство работающего оборудования.
- При изменении архитектуры, деплоя или пользовательского поведения обновлять соответствующие документы в том же PR.
- После изменения `AGENTS.md` проверять, что инструкции не противоречат действующим исходникам.
