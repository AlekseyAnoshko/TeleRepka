# Repka Pi Lab Hub

Веб-сервис информационной панели лаборатории на **Repka Pi 4**. 
Предполагается, что в офисном помещении есть несколько рабочих мест сотрудников и большой телевизор.
Миникомпьютер на телевизоре по HDMI в режиме киоска и совмещает четыре функции:

1. **Датчики** — температура и влажность (DHT11), качество воздуха (MQ-135) в реальном времени.
2. **Фоторамки** — статус подключённых устройств ESP32 PhotoFrame (см. `docs/REPKA_PI_PHOTOFRAME.md`
   в репозитории esp32-photoframe) через их REST API.
3. **Трансляция с рабочих мест** — любой сотрудник открывает страницу `/broadcast`
   со своего компьютера и выводит экран или камеру+звук прямо на ТВ лаборатории
   через WebRTC, без установки дополнительного ПО.
4. **Трансляция интерактивных сайтов** — предусмотрено три кнопки вызова любого сайта на экран телевизора с возможностью его управления с веб-страницы Repka Pi.

Repka Pi при этом одновременно: подключена к сети университета по проводному
Ethernet (`end0`), раздаёт Wi-Fi как хотспот для фоторамок сотрудников, и
выводит картинку на ТВ по HDMI. Такая сетевая схема описана в
`docs/REPKA_PI_PHOTOFRAME.md` — сервис ниже рассчитан именно на неё.

Проект реализован на Debian 12 (ARM), но может быть адаптирован и для российских операционных систем для ARM-архитектуры.

## Архитектура

```
                    ┌───────────── Repka Pi 4 ─────────────┐
  Ethernet (end0) → │  сеть университета                       │
  Wi-Fi hotspot   → │  ↔ фоторамки сотрудников (ESP32)         │
  HDMI            → │  ↔ телевизор лаборатории (Chromium kiosk)│
                    │                                           │
                    │  Flask + Flask-SocketIO (app.py)          │
                    │   ├─ sensors.py     — опрос DHT11/MQ-135  │
                    │   ├─ photoframes.py — опрос REST API рамок │
                    │   └─ WebRTC signaling (offer/answer/ICE)  │
                    └──────────────────────────────────┘
                                     ▲
                                     │ HTTPS + WebSocket
                       ┌──────────────────────────┐
                       │  Рабочее место сотрудника   │
                       │  открывает /broadcast        │
                       │  (getDisplayMedia/getUserMedia)│
                       └──────────────────────────┘
```

Видео/аудио с рабочего места идёт к ТВ напрямую по WebRTC (peer-to-peer),
Repka Pi выступает только сигнальным сервером — это разгружает и без того
слабый канал Wi-Fi/Ethernet платы от постоянной трансляции медиапотока.

## Почему обязателен HTTPS

Браузерные API `getDisplayMedia()` (захват экрана) и `getUserMedia()` (камера/
микрофон) работают только в защищённом контексте — то есть по HTTPS, кроме
адреса `localhost`. Поскольку сотрудники открывают страницу `/broadcast` по IP
Repka Pi в локальной сети, а не с `localhost`, без TLS браузер заблокирует
доступ к камере и экрану. Поэтому `app.py` поднимает сервер по HTTPS
с самоподписанным сертификатом (см. ниже).

## Установка

### 1. Системные зависимости

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-pip python3-venv chromium-browser
```

Для MQ-135 через ADS1115 (I2C):

```bash
pip3 install smbus2 adafruit-circuitpython-ads1x15
```

Для DHT11 отдельная библиотека не обязательна — датчик читается программным
bit-banging через прямые вызовы `RepkaPi.GPIO`, см. раздел «Датчики DHT11 и
MQ-135» ниже.

### 2. Python-окружение

```bash
mkdir -p ~/lab-hub && cd ~/lab-hub
# скопируйте сюда все файлы из этого проекта: app.py, sensors.py, photoframes.py,
# config.json, requirements.txt, templates/, static/ (если добавите свои стили)
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Если датчики физически ещё не подключены, `sensors.py` вернёт `None` по
соответствующим полям, и веб-интерфейс корректно покажет прочерк вместо
значения, без падения сервиса.

### 3. Самоподписанный TLS-сертификат

```bash
mkdir -p ~/lab-hub/certs
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout ~/lab-hub/certs/key.pem \
  -out ~/lab-hub/certs/cert.pem \
  -days 3650 \
  -subj "/CN=repka-pi4.local"
```

При первом заходе на `/broadcast` браузер сотрудника покажет предупреждение
о недоверенном сертификате — это ожидаемо для внутреннего инструмента,
нужно один раз нажать «Дополнительно» → «Перейти на сайт».

### 4. Настройте `config.json`

Впишите реальные IP-адреса фоторамок в локальной Wi-Fi-сети Repka Pi
(диапазон вида `10.42.0.x`, см. `docs/REPKA_PI_PHOTOFRAME.md`):

```json
{
  "photoframes": [
    { "name": "Фоторамка Иванова", "ip": "10.42.0.101" },
    { "name": "Фоторамка Петрова", "ip": "10.42.0.102" }
  ]
}
```

### 5. Автозапуск сервера (systemd)

```bash
sudo cp lab-hub.service /etc/systemd/system/
sudo nano /etc/systemd/system/lab-hub.service   # поправьте пути и User, если нужно
sudo systemctl daemon-reload
sudo systemctl enable --now lab-hub.service
sudo systemctl status lab-hub.service
```

### 6. Автозапуск Chromium в режиме киоска на ТВ

Требуется графическая сессия автологина (например, LightDM/lightweight X11 с
автовходом пользователя `user`) — иначе `DISPLAY=:0` будет недоступен.

```bash
sudo cp lab-hub-kiosk.service /etc/systemd/system/
sudo nano /etc/systemd/system/lab-hub-kiosk.service   # поправьте пути и User
sudo systemctl daemon-reload
sudo systemctl enable --now lab-hub-kiosk.service
```

Проверьте, что автовход в графическую сессию включён:
```bash
sudo raspi-config   # или repka-config, если доступен: System Options → Boot / Auto Login
```

## Датчики DHT11 и MQ-135

Оба датчика подключены напрямую к 40-pin разъёму Repka Pi 4. Текущая
распиновка использует **11-й вариант** `repka-config` (`I1 Pinout Options`),
который включает I2C2 — этот же вариант ранее использовался для W1-GPIO
(DS18B20); шину I2C2 он предоставляет без дополнительной настройки.

### MQ-135 через ADS1115 (I2C)

MQ-135 — аналоговый датчик, а у Repka Pi (как и у Raspberry Pi) нет
встроенного АЦП. Обязательно нужен внешний ADC-модуль — **ADS1115** по шине
I2C2:

| Сигнал | Пин ADS1115 / MQ-135 | Физический пин Repka Pi 4 | Имя |
|---|---|---|---|
| Питание ADS1115 | VDD | 1 или 17 | 3.3V |
| SDA | ADS1115 SDA | 27 | PD24 (I2C2) |
| SCL | ADS1115 SCL | 28 | PD23 (I2C2) |
| Общий провод | GND | 6, 9, 14, 20, 25, 30, 34 или 39 | GND |
| Питание нагревателя MQ-135 | VCC | 2 или 4 | 5V |
| Аналоговый выход MQ-135 | AOUT → вход `A0` ADS1115 | — | — |

Перед первым использованием MQ-135 требует **прогрев ~24 часа** для
стабилизации показаний — это общее требование для всех датчиков серии MQ.
Показания MQ-135 — это индекс общего качества воздуха (аммиак/бензол/
CO2-эквивалент по калибровочной кривой), а не прямое измерение CO2 — при
выводе на экран стоит явно обозначить единицу измерения.

### DHT11 (цифровой GPIO, bit-banging)

DHT11 использует собственный однопроводной протокол — он похож на 1-Wire,
но **не совместим** с драйверами `w1-gpio`/`w1-therm` и не регистрируется в
`/sys/bus/w1/devices/`. Читается программным bit-banging через прямые
вызовы `RepkaPi.GPIO.setup`/`GPIO.input` с точным таймингом. Готовые
библиотеки под классический Raspberry Pi (`Adafruit-DHT`, `dht-pi`) жёстко
привязаны к Broadcom-специфичному `RPi.GPIO` и не заработают на Allwinner H6
без переделки — надёжнее взять чистый Python-класс без сторонних
C-биндингов, реализованный через прямые вызовы `RepkaPi.GPIO`.

| Сигнал | Физический пин Repka Pi 4 | Примечание |
|---|---|---|
| VCC | 1 или 17 | 3.3V |
| DATA | 11 | требует проверки точного имени порта на конкретной плате |
| GND | 6, 9, 14, 20, 25, 30, 34 или 39 | — |

Резистор подтяжки **4.7–10 кОм** между DATA и VCC обязателен — аналогично
требованию для 1-Wire, открытый сток DATA-пина нуждается во внешней
подтяжке, либо используется готовый модуль DHT11 с резистором, уже впаянным
на плате.

Точное системное имя порта для физического пина 11 на Repka Pi 4
(Allwinner H6) нужно подтвердить на конкретной плате — так же, как ранее
было определено соответствие «физический пин 7 → PL10» для W1-GPIO:

```bash
python3 -c "import RepkaPi.GPIO as GPIO; GPIO.setmode(GPIO.BOARD); GPIO.setup(11, GPIO.OUT); GPIO.output(11, GPIO.HIGH)"
cat /sys/kernel/debug/gpio   # найти строку gpio-NNN, изменившую состояние
```

После подключения `sensors.py` нужно обновить: заменить заглушку
`humidity: None` на реальное чтение DHT11, и завести показания MQ-135 как
отдельное поле — фронтенд (`index.html`) уже имеет готовый слот `#s-hum`
для влажности, менять разметку не потребуется.

### `repka-config` на чистом Debian не работает

Официальная утилита `repka-config` (в норме позволяет выбрать вариант
распиновки через `I1 Pinout Options` без ручного overlay) рассчитана на
полный образ RepkaOS и падает на чистом Debian с ошибкой вида
`advanced_options: команда не найдена`, так как зависит от отсутствующей в
Debian вспомогательной инфраструктуры RepkaOS. На данной установке
(Debian 12 bookworm поверх Repka Pi 4) нужный вариант распиновки (11:
UART0 + PWM0 + I2C2 + W1-GPIO) включается только вручную, через device tree
overlay.

## Использование сотрудниками

Любой сотрудник в сети лаборатории открывает в браузере:

```
https://<IP Repka Pi>:5000/broadcast
```

Вводит своё имя, нажимает «Показать экран» или «Показать камеру + звук» —
трансляция сразу появляется плиткой на ТВ. Несколько сотрудников могут
транслировать одновременно, сетка на ТВ подстраивается автоматически.
Кнопка «Остановить» завершает трансляцию.


## Дальнейшее развитие

Раздел собирает все рассмотренные варианты расширения датчиков и связи —
как ориентир при выборе следующих шагов, без привязки к конкретному сроку.

Аппаратная платформа для всех дополнительных датчиков, которые физически
не размещаются рядом с самой Repka Pi: **ESP32 DevKit (30 pin, Wi-Fi +
Bluetooth, USB-UART мост CP2102)**. Эта плата уже используется как база для
уличного датчика DS18B20 ниже, и будет применяться для любых следующих
выносных датчиков — единая аппаратная база упрощает прошивку, отладку
через USB (CP2102 виден системе как обычный `/dev/ttyUSB*`) и подключение
к тому же Wi-Fi-хотспоту Repka Pi, что уже используется фоторамками.

### Уличный датчик через ESP32 (DS18B20) по Wi-Fi

Датчик DS18B20, ранее рассматривавшийся для прямого подключения к самой
Repka Pi, теперь выносится на улицу через отдельный узел на **ESP32 (30 pin,
Wi-Fi + Bluetooth, CP2102)**, подключённый к тому же Wi-Fi-хотспоту Repka Pi
(`10.42.0.x`), что и фоторамки сотрудников. Логика: провод до уличного
датчика тянуть неудобно, а раз ESP32 всё равно нужен физически на месте
установки, разумнее использовать уже поднятый Wi-Fi-хотспот Repka Pi, а не
поднимать отдельную инфраструктуру (LoRaWAN-шлюз) только для одного
датчика.

Технически эта связка проще, чем прямое подключение DS18B20 к самой
Repka Pi:

- ESP32 читает DS18B20 через стандартные библиотеки Arduino `OneWire` +
  `DallasTemperature` — без device tree overlay, без pinctrl-возни с
  `r_pio`/`pio`, без правки `repkaEnv.txt`. Один `#include` и несколько
  строк кода.
- Резистор **4.7 кОм** между DATA и 3.3V всё равно обязателен (это
  фундаментальное требование протокола 1-Wire независимо от платформы),
  либо используется готовый модуль/переходник с резистором, уже впаянным
  на плате.
- Для уличного гидрозащищённого щупа резистор физически размещается не
  в самом зонде (герметичная металлическая «пуля» на конце кабеля), а на
  переходной плате внутри корпуса ESP32 — вся электроника, требующая
  защиты от влаги, остаётся в одном закрытом месте.
- ESP32 подключается к Wi-Fi-хотспоту Repka Pi и отдаёт показания через
  собственный REST API (`GET /temperature` и подобные) — Repka Pi опрашивает
  его точно так же, как сейчас опрашивает статус фоторамок ESP32 PhotoFrame
  через `photoframes.py`. Не требуется отдельный MQTT-брокер или
  LoRaWAN-шлюз — достаточно того же HTTP-опроса, что уже реализован в
  проекте.

### Общие варианты связи для новых датчиков

Сводка возможных путей подключения датчиков к панели TeleRepka — для
выбора в зависимости от расположения датчика:

| Датчик | Расположение | Связь | Протокол на Repka Pi |
|---|---|---|---|
| DHT11 | Внутри помещения, у самой Repka Pi | Проводной GPIO (bit-banging) | `RepkaPi.GPIO` напрямую |
| MQ-135 | Внутри помещения, у самой Repka Pi | Проводной I2C через ADS1115 | `smbus2`/`adafruit-circuitpython-ads1x15` |
| DS18B20 (уличный) | На улице, вне помещения | ESP32 (30 pin, Wi-Fi+BT, CP2102) через тот же хотспот | HTTP REST-опрос, аналогично `photoframes.py` |

Общий принцип: датчики рядом с самой Repka Pi подключаются напрямую по
проводу (GPIO/I2C), датчики на удалении — через отдельный ESP32-узел на
Wi-Fi, который отдаёт показания по REST API так же, как сейчас
опрашивается статус фоторамок ESP32 PhotoFrame.

## Возможные доработки

- Подключить DHT11 и MQ-135 физически (пины определены выше, провода уже
  в наличии) и обновить `sensors.py`, чтобы он читал реальные показания
  вместо текущих заглушек.
- Проверить и, если нужно, скорректировать точное системное имя GPIO-порта
  для физического пина 11 (DHT11) на конкретной плате Repka Pi 4.
- Добавить пароль/токен для страницы `/broadcast`, если лаборатория открыта
  для внешних посетителей.
- Настроить TURN-сервер, если у части рабочих мест окажется симметричный NAT
  и одного STUN (`stun.l.google.com`) не хватит для установления P2P-соединения.
